# AMSM - Agent Memory System Ming

## 安装

1. 克隆到Hermes插件目录,CLI终端输入

        cd ~/.hermes/plugins/
       
        git clone https://github.com/abel-wxm/AMSM-Agent-Memory-System-Ming amsm

（注意，不要用Hermes的官方安装命令，因为它会默认用本仓库的名字命名本地文件夹，你安装后的文件夹名字会显得很长）

2. 在Hermes配置文件config.yaml中启用，

       memory:
          xxxxxxxxxxx
          xxxxxxxxxxx
          provider: amsm
   

4. 给AMSM配置模型，在辅助模型下增加
   
 ~/.hermes/config.yaml，添加模型配置

    amsm:
        provider: 
        model:
        base_url: 
        api_key: ''
        timeout: 120。
   
3.  重启Hermes即可生效

## 2026.05.25 (V3.0 更新)

**核心架构更新：**
1. **彻底解耦重构**：按多 Agent 并行开发标准，将系统自下而上划分为 `schema.py` (数据字典)、`config_params.py` (宏观参数与权重控制)、`scorer.py` (评分与提权引擎)、`retrieval.py` (包含防回环的 5 阶段检索体系) 与 `atomic.py` (新增强大的原子事实剥离引擎)。系统级消灭了魔法数字与硬编码，提高了系统的纯粹度。
2. **底层重生与防爆管调控**：引入了基于 `INJECT_SUPPRESS_MSG_COUNT` 和 `INJECT_SUPPRESS_CHARS` (当前会话不足20条消息或500字时自动进入抑制防爆模式) 的静默注入控制，新增了基于 `CONTEXT_WINDOW_THRESHOLD` (80%) 的上下文熔断保护。
3. **记忆碎片去重与关联**：修复了 FTS5 索引脱位与 C_score 连接失效等技术债，基于 `similar_to` 的链表自排重功能一次性上线成功。

**系统压测结果：**
- **无缝挂载**：系统已成功以原生 MemoryProvider (`AMSM-Agent-Memory-System-Ming`) 的身份透明注册进入 Hermes 框架。
- **极限并发仿真压力测试**：绕开抑制阈值，一次性向 Hermes SQLite 引擎注入 5000 条高复杂度、带有核心与事实标签的混合语义记忆碎片，**5000 条碎片的持久化写入仅耗时 0.11 秒**。
- **极致检索性能**：在全表全文检索能力双路合并、且加载复杂的衰减打分计算下，基于 5000 条数据体量的**精准召回仅耗时 0.006 秒 (6毫秒)**。表现极其优异，完美通过了全负荷抗压测试！

## 二、核心设计原则（继承自 v1.3，无变更）

- **会话隔离优先**：默认物理隔离，非授权不跨会话加载
- **元数据强制绑定**：所有语义片段必须绑定完整元数据
- **用户语义绝对保真**：AI 仅可优化表达形式，不可改动核心语义
- **AI 总结自进化**：渐进学习用户风格，逐步逼近专属范式
- **轻量化落地**：优先复用官方接口和成熟方案
- **对话优先**：用户操作优先通过自然语言完成

## 四、MemoryProvider 接口规范（官方 ABC）

来源：`agent/memory_provider.py`（Hermes 官方，lines 34-70）

```python
from agent.memory_provider import MemoryProvider

class HermesMemoirProvider(MemoryProvider):

    @property
    def name(self) -> str:
        return "hermes-memoir"                # 唯一标识符

    def is_available(self) -> bool:
        """
        检查插件能否激活。
        规则：不得发起网络请求。只做本地文件/环境检查。
        """
        return memoir_db_path.exists()

    def initialize(self, session_id: str, **kwargs) -> None:
        """
        Agent 启动时调用一次。
        职责：打开 memoir.db，加载当前会话上下文，检索公共记忆库。
        """

    def prefetch(self, query: str) -> str:
        """
        每轮对话前调用。
        职责：四维加权检索 → 返回注入 system prompt 的文本片段。
        返回值直接拼入上下文，务必控制长度（建议 ≤ 800 token）。
        """

    def sync_turn(self, turn_messages: list) -> None:
        """
        每轮对话结束后调用。
        职责：判断是否触发归档（token 阈值/语义边界），写入 memoir.db。
        异步执行，不阻塞主流程。
        """

    def shutdown(self) -> None:
        """
        Agent 退出前调用。
        职责：写回 WAL，关闭数据库连接，更新索引。
        """

    def post_setup(self, hermes_home: Path, config: dict) -> None:
        """
        可选。首次 hermes memory setup 时调用。
        职责：引导用户完成初始配置（归档阈值、公共库路径等）。
        """
```

## 六、存储层设计（SQLite-vec）

### 为什么换掉 Chroma

| 维度 | Chroma | SQLite-vec |
|---|---|---|
| 进程 | 需单独启动服务进程 | 单文件，随 memoir.db 一起打开 |
| 依赖 | chromadb + 依赖链 | sqlite-vec（单个 Python 包） |
| 与 Hermes 的关系 | 异构 | 同构（Hermes 原生用 SQLite） |
| 本地离线 | 支持 | 支持 |

### memoir.db 核心表结构

```sql
-- 语义片段主表
CREATE TABLE segments (
    id          TEXT PRIMARY KEY,          -- UUID
    session_id  TEXT NOT NULL,
    created_at  INTEGER NOT NULL,          -- Unix timestamp (秒)
    title       TEXT NOT NULL,             -- 智能小结
    keywords    TEXT NOT NULL,             -- JSON数组，3-5个关键词
    content     TEXT NOT NULL,             -- 片段正文
    weight      REAL DEFAULT 1.0,          -- 语义权重（人工总结=2.0）
    is_manual   INTEGER DEFAULT 0,         -- 是否人工总结
    is_public   INTEGER DEFAULT 0,         -- 是否已归档至公共库
    is_favorite INTEGER DEFAULT 0,         -- 是否收藏
    source_msgs TEXT,                      -- 原始消息ID列表（JSON）
    modified_at INTEGER,                   -- 最后修改时间
    FOREIGN KEY (session_id) REFERENCES sessions(id)
);

-- 向量索引（sqlite-vec 扩展）
CREATE VIRTUAL TABLE segments_vec USING vec0(
    embedding FLOAT[768]                   -- 向量维度按嵌入模型决定
);

-- 会话元数据表
CREATE TABLE sessions (
    id          TEXT PRIMARY KEY,
    name        TEXT,                      -- 用户自定义名称
    channel     TEXT DEFAULT 'cli',        -- cli/wechat/webui/...
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    core_tag    TEXT,                      -- 会话核心标签（动态更新）
    is_favorite INTEGER DEFAULT 0
);

-- 公共记忆库（来自各会话的精华）
CREATE TABLE public_library (
    id          TEXT PRIMARY KEY,
    source_seg_id TEXT NOT NULL,           -- 原始片段ID（双向索引）
    origin_type TEXT NOT NULL,             -- 'manual'/'favorite'/'auto'
    content     TEXT NOT NULL,
    keywords    TEXT NOT NULL,
    created_at  INTEGER NOT NULL
);

-- 自进化学习样本库
CREATE TABLE evolution_samples (
    id          TEXT PRIMARY KEY,
    original    TEXT NOT NULL,             -- AI原始总结
    edited      TEXT NOT NULL,             -- 用户修改后版本
    diff_score  REAL,                      -- 差异度（0-1）
    created_at  INTEGER NOT NULL
);
```

## 七、检索算法规范（四维加权）

```
score = (
    semantic_similarity × 0.5      # 向量余弦相似度
  + time_weight        × 0.3       # 指数衰减：exp(-λ × Δdays)，λ=0.05
  + tag_match          × 0.1       # 关键词命中率
  + user_weight        × 0.1       # 用户标记权重（归一化至0-1）
) × manual_bonus                   # 人工总结片段：× 2.0
```

默认检索范围：当前会话 + 公共记忆库  
跨会话检索：仅在用户显式触发时（`@session-xxx` 语法）

## 九、资源冲突处理（直接使用 v0.13 Kanban）

不再自建 resource_lock.yaml，改为：

1. 多个 Gateway 通道并发时，密集写入操作提交为 Kanban 任务
2. memoir.db 写操作统一使用 SQLite WAL 模式（原生支持多读单写）

4. Kanban 的心跳/僵尸检测负责处理进程崩溃后的锁释放

## 快速了解

### 项目是什么？

AMSM 是对 Hermes Agent 框架的记忆系统的完整重构方案。Hermes 作为一个成熟的 Agent 框架，其记忆系统存在以下痛点：
- 记忆管理不够直观，用户难以定制
- 记忆加载缺乏智能权重，历史事实和当下需求无法区分
- 无法学习用户的记忆策略，AI 总结停留在固定模板

AMSM 通过直接实现 Hermes 官方 MemoryProvider 接口，用 **几百行代码** 替换可能需要 **几千行** 的复杂破解方案，提供了一个**轻量、优雅、可演进**的解决方案。

### 为什么需要它？

| 场景 | 痛点 | AMSM 方案 |
|------|------|----------|
| 长期对话累积 | 老记忆淹没新记忆 | 时间权重衰减 + 用户标记优先级 |
| 跨会话知识复用 | 记忆孤立，无法跨会话检索 | 公共长期记忆库 + 显式跨会话引用 |
| AI 总结千篇一律 | 不符合用户习惯 | AI 自进化模块学习用户风格 |
| 重要内容容易丢失 | 没有系统的收藏/归档机制 | 完整的元数据体系 + 永久溯源 |
| 记忆系统故障影响主程序 | 没有隔离机制 | 记忆系统故障 100% 不影响 Hermes 主进程 |

### 核心数据指标（方案对比）

在发现 Hermes 官方 MemoryProvider 接口之前，我设计了三个技术方案。最终方案相比原方案的突破：

| 指标 | 原方案（破解黑盒） | 最终方案（官方接口） | 改进倍数 |
|------|----------------|------------------|--------|
| 代码工作量 | 几千行 | 几百行 | **↓ 90%** |
| 开发周期 | 几周 | 几天 | **↑ 10x** |
| 技术复杂度 | 高（黑盒破解） | 中等（官方接口） | **↓ 50%** |
| 系统稳定性 | 低（版本绑定强） | 高（跟随官方） | **↑ 大幅提升** |
| 可维护性 | 差（脆弱黑盒） | 优（标准接口） | **↑ 显著提升** |

## 核心设计总则（不可突破的底层规则）

| # | 原则 | 含义 |
|---|------|------|
| 1 | **会话隔离优先原则** | 每个独立会话默认物理隔离，仅加载自身会话文件夹内的历史内容，不同会话间互不干扰 |
| 2 | **元数据强制绑定原则** | 所有会话、语义片段必须绑定标准化元数据，作为检索、溯源、管理的核心依据 |
| 3 | **检索权重动态适配原则** | 用户主动指定的检索条件最高优先级；无指定时执行系统默认「先会话级、后片段级」排序 |
| 4 | **记忆全链路可溯源原则** | 所有归档内容永久留存原始会话来源路径、创建通道、操作日志，支持一键定位 |
| 5 | **用户自定义语义绝对保真原则** | 用户发起自定义总结时，AI 仅可完善表达形式（语句通顺、标点修正、格式统一），绝对不可修改语义 |
| 6 | **AI 总结自进化原则** | AI 自动总结持续学习用户人工总结的风格、关注重点、取舍逻辑与表述习惯，逐步优化 |
| 7 | **轻量化落地原则** | 优先复用开源、成熟、多人验证的稳定方案，易维护、可快速落地 |
| 8 | **对话优先原则** | 用户操作优先通过自然语言对话完成，UI 交互补充 |

## 核心功能需求

### 3.1 会话管理模块

- **P0 会话基础生命周期管理**
  - 新建会话自动生成独立文件夹和元数据
  - 删除会话同时删除对应文件夹和所有数据
  - 会话列表按最后更新时间倒序排列

- **P0 用户自定义会话名称**
  - 支持通过对话及手动方式修改会话名称：`"把这个会话改名为xxx"`
  - 修改后自动更新文件夹名称和所有关联元数据
  - 历史名称留存于操作日志

- **P1 会话收藏功能**
  - 支持通过对话方式收藏/取消收藏会话：`"收藏这个会话"`
  - 收藏标记写入会话元数据，同步存储至公共记忆库
  - UI 界面专门增加收藏列表，可按其他元数据（时间、来源、标签等）排列

- **P1 多通道消息隔离**
  - 不同通道（UI/CLI/微信等）的会话存储逻辑同普通会话，仅文件夹命名加上来源信息
  - 支持显式跨通道引用会话

### 3.2 记忆存储模块

- **P0 语义片段化存储**
  - 按语义边界切分对话，不保存整条原始消息
  - 切分算法三模式加权：话题边界(0.6) + 时间间隔(0.2) + 长度限制(0.2)
  - 单个片段长度控制在 1-500 字之间

- **P0 用户自定义总结双流程**
  - 触发场景：用户说 `"刚才这段的总结是xxx"` （支持文本/语音输入）
  - 默认流程（语义保真优化确认）：
    1. AI 接收用户总结，仅做语句通顺、标点修正、格式统一
    2. 向用户展示优化后版本：`"我帮你整理了一下，你看这样可以吗？"`
    3. 用户确认后，添加标签归档
    4. 人工总结语义权重为 AI 自动总结的 2 倍，AI 不再自动更新该片段

- **P0 语义权重标记与学习机制**
  - 支持用户通过对话标记权重：`"这个很重要，权重设为2"`
  - 权重直接影响检索排序及 AI 学习样本

- **P1 多维度标签系统**
  - 自动生成时间/关键词/话题三类标签
  - 标签检索权重 0.2

- **P3 Markdown 文档生成**
  - 支持人工指定记录，生成 Markdown 文件（不打开软件也可阅读）
  - 支持用户修改的 Markdown 记录同步至公共记忆库

### 3.3 记忆检索模块

- **P0 原生自动检索注入**
  - 每次用户发消息自动触发检索
  - 检索结果自动注入 Hermes 系统提示词
  - 全程对用户透明

- **P0 四维加权检索算法**
  - `语义相似度(0.5) × 时间权重(0.3) × 标签匹配度(0.1) × 用户标记权重(0.1)`
  - 人工总结片段基础权重翻倍
  - 时间权重采用指数衰减函数

- **P0 会话隔离机制**
  - 默认仅检索当前会话记忆
  - 不同会话记忆空间完全独立

- **P1 跨会话引用支持**
  - 支持特殊语法引用：`"@session-2026-05-11 关于Hindsight的讨论"`
  - 支持按话题、关键词、时间范围批量引用

- **P2 跨通道引用支持**
  - 支持指定通道引用：`"@cli 2026-05-10 环境配置"`

### 3.4 记忆管理模块

- **P0 基础 CRUD 操作**
  - 支持通过对话查看、编辑、删除任意记忆片段
  - 所有操作记录永久留存

- **P1 记忆搜索界面**
  - 支持按关键词、标签、时间范围搜索
  - 搜索结果可直接编辑删除

- **P1 公共长期记忆库**
  - 支持用户手动或语音指定 AI 将重要片段同步到公共库
  - 公共库内容所有会话均可检索
  - 保留原始会话溯源信息

### 3.5 AI 自进化模块

- **P0 总结风格学习**
  - 所有用户人工总结自动加入 AI 学习样本库，AI 根据权重学习
  - 学习用户的总结长度、关注点、表述习惯
  - 定期更新 AI 总结模型参数

- **P1 权重偏好学习**
  - 学习用户标记重要性的模式

- **P1 标签偏好学习**
  - 学习用户手动修改标签的习惯
  - 优化自动标签生成算法

## 技术方案演化

### 初期困境（2026-05-04 ~ 2026-05-10）

最初我错误假设 Hermes 记忆系统是**完全封闭的黑盒**，规划了三个技术方案来绕过官方系统。

详见 [BACKSTORY.md - 初期困境](./BACKSTORY.md#初期困境2026-05-04--2026-05-10)

### 重大突破（2026-05-11）

在深入研究 Hindsight 源码时，发现了 **Hermes 官方提供了标准 MemoryProvider 接口**，彻底改变了整个项目的复杂度。

详见 [BACKSTORY.md - 重大突破](./BACKSTORY.md#重大突破2026-05-11)

### 最终技术路线

**纯原生实现，零第三方依赖**：

- ✅ **直接实现** Hermes 官方 MemoryProvider 接口
- ✅ **通过插件系统注册**，完全替换原生记忆系统
- ✅ **必须实现**：插件注册逻辑、Chroma 集成、核心业务逻辑
- ✅ **完全不需要实现**：数据库监听、定时任务、记忆注入、多会话管理

## 经验教训与行动指南

### 四个核心经验教训

1. **任何时候行动前，先查官方接口，再考虑自己实现**
   - 成熟框架通常已有扩展点，值得深入挖掘

2. **不要默认假设官方没有扩展点**
   - 官方文档和源码是最快的参考

3. **生态比技术更重要，避免重复造轮子**
   - Hindsight 的存在本身就是一个信号

4. **核心业务逻辑才是竞争力，样板代码可以借鉴**
   - 真正的竞争力在于智能算法创新，不是工程复杂度
